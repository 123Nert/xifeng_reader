# xifeng 阅读 · 技术方案（MVP）

> 对应《产品设计文档.md》，产品范围以产品设计文档为准，本文档回答"怎么实现"。
>
> 总原则：**P0 功能全部用浏览器原生能力实现，零后端、零原生依赖**；保持 UI 层可整体移植，
> 为将来 Tauri 桌面壳与云同步留出空间。

## 1. 选型总览

| 层面 | 选型 | 说明 |
| --- | --- | --- |
| 构建工具 | Vite + TypeScript (strict) | 产物为纯静态文件，任意静态托管可部署 |
| UI 框架 | React | 生态成熟；本应用仅两个视图，若偏好 Vue/Svelte 替换成本极低 |
| 状态管理 | React 内置 useState / Context | 应用只有两个视图，不引入 Redux 等重型方案 |
| 路由 | 暂不引入路由库 | 书库 / 阅读页由状态切换；将来需要浏览器前进后退时再引入 react-router |
| 持久化 | IndexedDB（书正文、进度）+ localStorage（设置） | 完全本地，无服务端 |
| 编码解码 | 浏览器原生 `TextDecoder` | 零依赖实现 UTF-8 / GB18030 探测与解码 |
| 样式 | 原生 CSS + CSS 变量 | 对应产品设计文档"主题用 CSS 变量预留"的要求 |
| 测试 | Vitest | 覆盖 core 纯逻辑模块 |
| 运行时依赖 | react、react-dom、idb | `idb` 仅是 IndexedDB 的 Promise 封装（约 1KB），其余为零 |

### 为什么不是 Electron

Electron 本身是成熟方案，但本期 P0 功能（文件导入、编码识别、分页、本地存储）全部是浏览器
原生能力，引入 Electron 意味着先背上约 100MB 的安装包与完整 Chromium 运行时，而换来的系统能力
一项都用不上。因此维持产品设计文档的路线：**先做纯 Web；桌面化需求出现时用 Tauri 2.x 包装**
（复用系统 WebView，安装包 10MB 以内、内存占用低，对常驻阅读场景更友好）。

现阶段唯一要守住的红线：**任何功能不得依赖 Node / 原生 API，必须纯浏览器可运行。**

## 2. 总体架构

- **UI 层（React）**
  - `LibraryPage`（书库）：导入、列表、删除
  - `ReaderPage`（阅读）：分页渲染、翻页、工具条、进度条
- **core 层（纯 TypeScript，框架无关、可单测）**
  - `encoding`：编码探测与解码
  - `pagination`：分页引擎（核心）
  - `bookRepository`：IndexedDB 读写封装
  - `settings`：阅读设置读写
- 依赖方向：UI 层 → core 层 → 持久化；core 层不感知 React。

## 3. 核心设计

### 3.1 文件导入与编码识别

**流程**：文件选择 / 拖拽 → 读取 `ArrayBuffer` → 编码探测 → 解码为字符串 → 入库 → 返回书库。

**编码探测算法**（按序执行）：

1. BOM 检查：`EF BB BF` → UTF-8；`FF FE` / `FE FF` → UTF-16LE/BE（低频但零成本，顺手支持）。
2. 无 BOM 时：`new TextDecoder('utf-8', { fatal: true })` 全量严格解码，成功即判定 UTF-8。
   UTF-8 校验是极强的信号——GB18030 文本恰好整体构成合法 UTF-8 的概率可忽略。
3. 严格解码抛错 → 回退 `TextDecoder('gb18030')` 解码。GBK 是 GB18030 的子集，且按 Encoding
   Standard 规范 `gbk` 标签本就映射到 gb18030 解码器，取超集即不会丢字。

**说明**：不引入 chardet 类第三方探测库。它们面向任意语种编码（日/韩/西文等），而本产品只需
覆盖中文 TXT 的实际分布，上述两步探测即满足验收标准第 1 条，且零依赖。

### 3.2 存储设计

IndexedDB 数据库 `xifeng-reader`（v1）：

| Object Store | keyPath | 记录结构 |
| --- | --- | --- |
| `books` | `id` | `{ id, title, content, size, charset, importedAt }` |
| `progress` | `bookId` | `{ bookId, charIndex, updatedAt }` |

localStorage：`xifeng.settings` → `{ fontSize, lineHeight }`（深色主题字段预留）。

设计要点：

- **进度与正文分 store**：进度每次翻页都要写入；若与几 MB 的正文同记录，每次翻页都会重写整条
  大记录。分开后进度写入只有几十字节。
- `id` 使用 `crypto.randomUUID()`；`title` 取文件名去掉 `.txt`。
- **重复导入**：MVP 直接作为新书入库（同名旧书可手动删除），不做内容级去重。以书名作主键会让
  "同名不同书"互相覆盖，弊大于利。
- 正文以字符串（而非 Blob）入库：分页引擎直接消费字符串，避免每次打开都重新解码；原文件编码
  记录在 `charset` 字段，将来需要"导出原文"时可用。

### 3.3 分页引擎（核心）

**数据模型**：全文在内存中就是一个字符串（百万字 ≈ 2~6 MB，无压力）；"一页"是字符区间
`[start, end)`。渲染层每次只把当前页的子串放进 DOM。"懒加载"发生在两个层面：DOM 只渲染当前页，
页界按需计算——这就是产品设计文档"大文件分块/懒加载"要求的落点。

**页界计算**（两步）：

1. **容量估算**：用与正文同宽、同字体设置的离屏元素，测出"每行字符数 × 每页行数"的粗略容量 C。
2. **二分精化**：`fits(start, n)` 将 `text.slice(start, start + n)` 放入离屏元素实测渲染高度是否
   ≤ 页高；在 C 的 ±50% 邻域内二分求最大的 n，页界即 `start + n`。单次页界计算是几十次 DOM
   读写，毫秒级。

**惰性页界缓存 `PageMap`**：`pageStarts: number[]` 只记录已计算过的页起点。向后 / 向前翻页时增量
计算相邻页界并缓存；跳转时按 `pos / C` 估算页号，从最近的缓存边界推进；MVP 简化：跳转后丢弃其后
的缓存页，从新页界继续。

**锚定重排**：字号 / 行距变更、窗口 resize（去抖）时，重新测容量 C，以"当前页首字符偏移"为锚点
重新 fit 当前页界，并清空后续缓存。这样保证设置变更后阅读位置不丢（验收标准第 5 条）。

**段落处理**：正文用 `white-space: pre-wrap` 直接呈现原文换行；允许在段落内部断页（长篇正文
天然流动，MVP 不做孤行控制）。

**可测试性**：`fits` 依赖真实 DOM 布局（jsdom 不做布局），因此分页引擎拆为两层：

- `Measurer` 接口：DOM 相关，由 UI 层注入；
- `PageMap`：纯逻辑（缓存推进、锚定、跳转数学），单测注入假 Measurer 即可覆盖。

**被否方案**：CSS 多栏（column-width = 页宽 + 横向滚动）可让浏览器"免费"分页，但拿不到精确的
字符偏移——进度记忆与跳转都做不准，且超长内容下列布局有性能风险，故不采用。

### 3.4 阅读进度与交互

- 进度保存时机：每次翻页即写 `progress`（写入量极小，无需去抖）。
- 进度条：拖动值 p ∈ [0, 1] → 目标字符偏移 `round(p × (totalChars - 1))`，交给 PageMap 定页。
- 翻页输入：按钮、键盘 ← → / 空格、点击正文左右 1/3 区域；触摸滑动非 P0（V1）。
- 续读：打开书时读取 `progress.charIndex`，从该偏移定页渲染（验收标准第 3 条）。

### 3.5 样式与主题

- 全部视觉参数走 CSS 变量，正文排版只引用变量、不写死数值：

```css
:root {
  --bg: #fafaf7;
  --text: #2c2c2c;
  --content-font-size: 18px;   /* 由 JS 动态写回 */
  --content-line-height: 1.8;
}
```

- 字号 / 行距调整通过 `document.documentElement.style.setProperty` 写回；分页测量与正文渲染共用
  同一组变量，保证"所见即所测"。
- 深色主题（V1.1）= 新增一组 `.dark { --bg: …; --text: …; }` 变量，其余零改动。


## 5. 测试策略

按 AGENTS.md 约定：每次改动交付前必须全部测试通过，并创建对应的 Git commit。

| 模块 | 测试内容 |
| --- | --- |
| `encoding.ts` | 构造 UTF-8 / GBK / GB18030 / UTF-16 / 带 BOM 的 fixture 字节流，断言探测与解码结果 |
| `pagination.ts` | 注入假 Measurer，覆盖：页界单调性、前后翻页、跳转数学、锚定重排后位置不变 |
| `bookRepository.ts` | 基于 fake-indexeddb 的书籍增删查、进度读写 |
| UI 层 | MVP 以产品设计文档 §6 验收清单做手动验收；V1.x 引入 Playwright 做 E2E |

## 6. 运行与部署

- 开发：`npm run dev`（Vite dev server，localhost）。
- 构建：`npm run build` 产出纯静态文件，可部署到任意静态托管。
- **注意**：IndexedDB 在 `file://` 协议下不可用，直接双击打开 HTML 不能作为使用方式；开发与部署
  必须走 http(s) / localhost（这也是将来桌面化需要壳的原因之一）。
- Node ≥ 20。

## 8. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 分页测量依赖真实布局，jsdom 无法覆盖 | `fits` / Measurer 已接口化隔离，核心逻辑用假 Measurer 单测；真机手感以手动验收兜底 |
| 页界二分的 DOM 测量在低端设备变慢 | 测量元素脱离文档流且复用单实例；必要时对 ASCII 段落走等宽近似通道（预留优化，不预先实现） |
| 超大文件（数百 MB） | 明确不支持。百万字 ≈ 2~6 MB，整串内存方案余量充足；更大文件属未来流式分块议题 |
| TextDecoder 老浏览器兼容 | 目标为现代常青浏览器（Chrome / Edge / Firefox / Safari 近两年版本），不做兼容降级 |
